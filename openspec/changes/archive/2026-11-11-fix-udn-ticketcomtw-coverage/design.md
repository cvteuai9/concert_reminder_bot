## Context

延續修 KKTIX 分頁時使用者問的問題——其他來源是否也有「只抓到部分活動」的問題。逐一比對實際頁面內容與目前 scraper 回傳結果後,確認:

**udn售票網**:首頁有三個分類頁籤(`#yd_showRecommend-tab`「推薦節目」、`#yd_showRecent-tab`「近期節目」、`#yd_showPackage-tab`「套票組合」),三個頁籤的卡片都已經在同一次首頁請求拿到的靜態 HTML 裡(ASP.NET WebForms 常見做法:所有分頁內容都渲染到 HTML,只是用 CSS/JS 切換顯示哪一個)。但卡片的內部結構三者不完全一樣:
- 推薦節目:`<h5 class="yd_card-title">`,連結是 `?PRODUCT_ID=...`
- 近期節目:`<h5 class="yd_card-text" itemprop="name">`,連結同樣是 `?PRODUCT_ID=...`,但標題 class 不同
- 套票組合:`<h5 class="yd_card-title">`(跟推薦節目一樣),但連結是 `?AGId=...`(不是 `PRODUCT_ID`)

目前的 `udn.py` 只處理「推薦節目」那種組合(`.yd_card-title` + `PRODUCT_ID`),導致另外兩個頁籤的 23 張卡片(總共 35 張裡)被跳過。

**年代售票 Ticket.com.tw**:使用者實測發現 `UTK0101_06.aspx?TYPE=1&CATEGORY=205` 是官方的「演唱會節目總表」頁面,卡片結構是 `div.moreBox`,內含 `.list-group-item-heading`(標題)、`.list-group-item-date`(日期),沒有分頁、沒有大圖輪播那種空白 alt 的問題。這個頁面抓到 13 筆,比原本首頁兩個部件(本月熱門輪播 + 即將開賣輪播)合計的 11 筆(且其中還混了 8 筆完全沒有文字可抓的大圖輪播連結、根本進不了結果)更完整也更乾淨。

## Goals / Non-Goals

**Goals:**
- udn:同時支援三種卡片的標題結構(`.yd_card-title` 或 `.yd_card-text`)跟兩種連結參數(`PRODUCT_ID` 或 `AGId`),涵蓋所有頁籤的卡片
- ticket_com_tw:改用使用者找到的完整節目總表頁面,取代原本解析首頁兩個輪播部件的做法

**Non-Goals:**
- 不處理 ibon、遠大售票 Ticket Plus——使用者已經確認這兩個平台現有的 API 回傳的就是完整資料,不需要調整
- 不嘗試去找年代售票是否還有其他 `CATEGORY` 代碼對應其他类型的演出(例如音樂劇、展覽)——使用者這次要的是「演唱會」,`CATEGORY=205` 這個頁面的名稱本身就是「演唱會節目總表」,范圍符合需求;如果之後想擴大涵蓋其他類別,再另外處理
- 不處理年代售票這個新頁面本身是否有分頁——實測沒有分頁控制項,13 筆看起來就是全部;如果之後筆數成長到需要分頁,屆時再補

## Decisions

### udn:標題用「`.yd_card-title` 優先、沒有的話退回 `.yd_card-text`」,連結用「同時接受 `PRODUCT_ID` 或 `AGId` 兩種參數名稱」
不去區分這張卡片屬於哪個頁籤(不特別去判斷在哪個 `<div id="yd_show...-tab">` 底下),純粹讓選擇器本身夠寬容去涵蓋三種卡片的所有變體。這樣之後如果 udn 再新增第四種頁籤組合,只要還是用同一套 `yd_card-*` 命名慣例,大概率也能自動被涵蓋,不需要每次改版都重新調整。

### ticket_com_tw:整個換成節目總表頁面,原本的兩個首頁輪播解析邏輯整段移除
不是「兩者都抓、取聯集」,而是直接用使用者找到的這個更完整的單一頁面取代。原因:首頁的「本月熱門」輪播是這個總表頁面的子集(同樣的活動,只是精選呈現),「即將開賣」輪播則是另一種呈現(開賣時間而非場次日期),混用兩套資料來源反而增加維護負擔;改成單一個資料來源後,`_add_event`/多選擇器合併的邏輯可以整段刪除,程式更簡單。

## Risks / Trade-offs

- **[風險] 年代售票的節目總表頁面之後可能改成有分頁,到時候現在「一次請求抓完」的假設會失效。** → 緩解方式:沿用既有的錯誤隔離模式,即使之後真的加了分頁,在修好之前也只是「抓到的筆數變少」而不是整個來源壞掉;屆時可以參考這次 KKTIX 分頁的做法(區分「這頁失敗」跟「真的到底了」)來修。
- **[風險] udn 放寬選擇器(同時接受兩種標題 class、兩種連結參數)可能在未來版面改動時,意外吃進一些不相關的卡片(例如真的不是售票活動的推廣連結)。** → 緩解方式:`artist-watch-matching` 的比對邏輯只看標題關鍵字,多抓到幾筆不相關的活動不會造成誤通知,風險可接受。
